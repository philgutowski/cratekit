# U64 mutation table, author's

**Verdict.** Twenty five rows over the playlists exclusion rules, the cursor and
the adapter's account listing. Twenty four kill on their subsets. One zero on the
first pass, C2, was user facing and asked for a test, now added. One zero
remains, C3, maintainer facing, promoted to the full suite and still zero there.

**How it was measured.** Not by `scripts/mutate.py` end to end, because its
preflight is two full suite runs of about 390 seconds each and cannot finish
inside a relay task's ten minute foreground call (R-329). Each row was run through
the driver's own functions from `docs/mutation/u64-rows.toml`: `load_spec` read the
rows, `mutated` applied each one alone and restored it, `verify_restore` checked
the restore against `git show HEAD:<path>`, and `run_pytest` counted deaths off
report objects with `PYTHONDONTWRITEBYTECODE=1`. A green subset baseline was run
before the rows of each subset, and every row's collected count matched its
baseline. No null control row was run. The rows file's batch name is
`u64-driver`, so an attended driver run writes beside this file rather than over
it.

**The author could not kill nothing, which is a claim about the author.** No
independent table was run.

## The zeros

- **C2.** No test queued a job against another volume, so the filter that keeps
  one library's sweep out of another library's cursor guarded nothing the suite
  reached. `test_another_librarys_finished_job_is_not_this_librarys_sweep` queues
  a succeeded job under a different volume identifier and drives a pass.
- **C3, maintainer facing, one line.** Nothing produces a job carrying
  `source_id` `playlists` under any key but `intake.playlist`: the favourites and
  labels jobs carry their own source identifiers, so the other two filters cover
  every reachable input. Kept as defence and filed as R-364.
