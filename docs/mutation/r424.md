## What the one zero row found, and what was done about it

Written by the author after the batch, above the driver's own output, because
the driver reports what it measured and this is what the measurement changed.

`D2_filed_filter` killed nothing on the subset and nothing on the promoted full
suite. The filter it deleted is user facing: it is what keeps a source that
queued nothing from reporting warnings about work that did not happen, and
this closure's standing warning is the first one it holds back.

The zero was not the filter's. It was the guard's.
`test_a_declined_favourites_source_says_nothing_about_a_write_it_never_reached`
was written with no label registered, so every source refused, nothing queued,
and `crate sync all` RAISES before it reaches the warnings loop at all. The
envelope it asserted over carried no warnings whatever the filter did. The test
passed, and would have passed with the filter deleted, with `plan.warnings`
deleted, or with the whole loop deleted. That is this repository's first
recurring defect pattern exactly: an absence read as evidence of absence.

The guard now registers a label, so the labels sweep queues, the pass exits OK
and the loop runs. Re-measured by hand after the batch, the same mutation as
`D2_filed_filter` applied to the same site with `PYTHONDONTWRITEBYTECODE=1`
set: 1 killed, `test_a_declined_favourites_source_says_nothing_about_a_write_it_never_reached`,
over 77 collected against a baseline of 77. The source was restored by
rewriting it and verified byte identical against `git show HEAD:`.

One row is therefore measured outside the table above, and the table above is
the state of the branch when the batch ran rather than the state it merges in.
Both numbers are here rather than only the second.

## The one row whose number is not what it looks like

`B4_warning_copied` is recorded above as 20 kills, promoted. Read the word
promoted: the subset killed ZERO, and the 20 came from the full suite run the
driver does before it will report a zero. All 20 are in `tests/test_rebuild.py`,
a file with no path to the favourites warning at all.

Driven after the batch rather than argued. The same mutation was applied to the
same site with `PYTHONDONTWRITEBYTECODE=1` set, and `tests/test_rebuild.py` was
run alone: 103 passed. The file was restored by rewriting it, verified byte
identical against `git show HEAD:`, and run again: 103 passed. So the mutation
does not produce those failures, and the 20 is not attributable to this line.

**`B4_warning_copied` is therefore a ZERO on a maintainer facing guard, and it
gets this line rather than a composite.** Nothing in the suite notices whether
`local_write_warning` copies the dict it returns. The copy stays because the
returned warnings travel into a renderer and into json and a caller handed the
module level object could edit the sentence every later pass reports, which is
an argument for the line and not a measurement of it. What the 20 actually
were was not chased: they belong to another file and another unit, and the
full battery is run below on the merged branch, which is where a real failure
in that file would appear.
