**The check.** `tagging/searchers.py` gains `DISCOGS_IDENTITY`
(`https://api.discogs.com/oauth/identity`), `TokenVerdict`, `TokenCheck`,
`DiscogsAsker.identity()` and `check_discogs_token(token, fetch=None,
sleep=None)`. The check builds a fresh asker with `discogs_asker`, exactly as
a sweep does, never the process's shared one (which holds the recorded
token), and makes one call through the asker's own `_read`: the
`Cratekit/<version>` agent, the `Authorization: Discogs token=...` header,
the pacer, the remaining count wait, `default_fetch`'s timeout and 429
ladder. A JSON object naming the account by an integer `id` is ACCEPTED; a
401, or a token that is not one printable word (never sent), is REJECTED; a
block, a challenge, a spent 429, a 5xx, a transport failure, a page that is
not JSON or names no account is UNCHECKED. Every note comes from `_said`,
which scrubs the token; the username Discogs returns is not kept.

**The step.** `cli/setup.py`'s credential loop passes over
`credential.discogs` (`DISCOGS_CHECK`), and `_link_discogs` runs after it,
offered where `doctor.offered` offered the token before. It writes what
Discogs is for, that a track Beatport does not carry stays untagged without
it, that it is free with a Discogs account, and where to make a personal
access token (`discogs.com/settings/developers`, Generate new token), then
asks `Link Discogs now?`, yes by default and a no when nothing can be asked.
The token is read through `Prompter.secret`, the line "Checking the token
with Discogs..." is written before the call, and the token is stored through
the new shared `_store` (`secrets.set` under `discogs-token`, as `crate
login` stores it) only when ACCEPTED, or UNCHECKED on a first link, which the
brief ruled. A rejected token is said on the terminal and asked again, three
tries in all (`DISCOGS_TRIES`, the prompter's `MAX_ATTEMPTS`), and never
stored; three refusals end in an INFO note. Declining, an unanswerable
question or an empty entry is an INFO note saying what is lost and naming
`crate setup` and `crate login discogs-token --from-file PATH`. A recorded
token is acknowledged (OK) with no question and no request; `crate setup
--relink-discogs` offers to replace it, and a replacement is stored only
when Discogs ACCEPTS it, so a refused or unchecked replacement keeps the
recorded token (round one), the unchecked note naming the login way round
(round two). A presence index it cannot read, a secret reader that fails, a
store that refuses, and any exception from the check (round one: a server
posing as Discogs can make the JSON reader raise) are notes, never raises,
with nothing stored. When Discogs is linked, `_discogs_vocabulary` asks
`taxonomy_upgrade.planned` and, for a copy lacking `[vocabulary.discogs]`,
adds an INFO note with the upgrade's own remedy (`crate taxonomy upgrade`);
a copy it cannot read or compare is left to doctor's taxonomy lines in the
same report. Doctor's checks are unchanged.
