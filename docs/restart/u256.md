**U256, #685, the suite builds its fixture rekordbox database once per
worker and copies it for each test, built in the cloud lane on 2026-11-12.**
Filed from the speed survey of 2026-11-12. Size medium: tests only, nothing
under `src` changes.

**What landed.** `tests/test_rb_writer_db.py::_build_disposable_database`
keeps its signature and its 27 calling files. Its old body is
`_build_from_nothing(db_path, *, with_tag_category, db_version)`, unchanged
but for taking the schema pin as an argument. The first call in a process for
each pair of `with_tag_category` and `W.pinned_db_version()` (the pin read at
every call, as the build always read it, so a test that configures another
pin before it builds still finds it in its file) builds the database from
nothing inside a `TemporaryDirectory` of its own, refuses if anything but the
one folded file is left beside it, reads it into `_TEMPLATES` as bytes, and
removes the directory. Every call then writes those bytes to its own path
with an exclusive create, at 0644 as SQLite creates a database. The template
exists only as immutable bytes in the
worker's memory, so no test can open, write, encrypt or delete it, and no two
tests share a file. A path where the database or any of its `-wal`, `-shm` or
`-journal` files already exists is built from nothing as before, so whatever
SQLite made of such a path, it still makes: a second build over the same
database still raises the integrity error it raised.

**The stamps, driven rather than argued.** A copy carries the time its
variant was first built in the process. One full run with every timestamp in
the template (`created_at`, `updated_at`, `date_1`, `date_2`) forced to
2001-01-01, a throwaway edit never committed, passed 18,485 and failed
exactly the base's 161 ids, so no test reads the fixed rows' stamps as
fresh. No restamp on copy.

**Measured, one run each on a quiet four core container.**
`MetaData.create_all` over a full run, counted with a throwaway plugin:
2,694 on the base (330, 753, 654 and 957 on four workers), 27 on the branch,
two per worker plus 19 on the worker that ran the new test file, whose tests
empty the cache on purpose. None of the rest of the suite took the from
nothing path for an existing file. A full run: 494.5 s at the baseline,
350 s on the branch. `--durations=20` before and after, one run each: the
same twenty guard and pool tests in both, none of them a database fixture,
since no fixture set up was ever in the top twenty; the first is
`test_the_collected_count_survives_parallel_workers`, 45.1 s before and
38.3 s after.

**Tests.** `tests/test_fixture_database_template.py`, thirteen: a copy written
to, altered and encrypted leaves its sibling and the next copy byte for byte
unchanged; a copy equals a build from nothing table by table and row by row,
schema, journal mode, user version, application id and page size with them,
the stamps read as set or not, for both variants; four builds of each
variant create the schema twice and give eight inodes; the pin read at the
call reaches `DBVersion` through the cache; a path holding the database or
any sidecar, empty, takes the from nothing build; a second build over a
database still raises; the rows the safety chain reads, named in the test
rather than read back from the builder, for both variants; a copy and a
build from nothing both at 0644 under umask 002.

**Decided by the session, recorded here.** The template is bytes in memory
rather than a file in a per process directory, as the brief's approach
suggested, so that "no test ever opens the template itself" holds by
construction rather than by care, and nothing is left on disk to clean up.
The cache key carries the schema pin. The existing path fallback keeps
today's behaviour exactly rather than overwriting.
