**U225, #577, a sync pair after a stopped order write finishes it from the
leading side, never copying the stopped write's account order into
rekordbox, built in the cloud lane on 2026-11-06.** A large card: it changes
what a write over both sides of a pair is planned from. Ordered behind U226,
which landed first. Filed from the attended sitting for A99: Sitting 62's run
added six tie tracks to `GIG READY Phil Sets Classic Soul Intro` and stopped
part way through ordering it, and a fresh `crate sync pair` planned
`order follows the account's` with a rekordbox `order` of the scramble. The
pair's snapshot never moved, so the merge read the stopped write's own moves
as the person's reorder on the account.

**What landed.**

- **The write's steps say what its order was doing.** `STEP_ACCOUNT` now
  records when the account write began, and `STEP_ORDERING` records a detail
  (`sync/pair_stopped.ordering_step`): when the order began, the account order
  it starts from (the listing the plan read with the removals and additions
  the adapter answered as landed), the order it asks, the side that led,
  rekordbox's memberships as they stood, whether this write committed them,
  and the links it made, which its snapshot would have recorded. The only
  other reader of either step, `check()`, tests presence, so nothing else
  reads the value.
- **A fresh plan reads every kept run's steps.** `core/held_plan.recorded_steps`
  reads each steps file younger than `KEEP` and names any it cannot read,
  said on the gate as `sync-pair-stopped-unread`. `pair_stopped.stopped_writes`
  takes, per account playlist, the latest write that began to order and never
  finished, unless a run that began its account write later finished the
  pair; `_Reader.stopped_write` keeps it only when it began after the pair's
  snapshot.
- **Its moves are not the person's.** `pair_stopped.passed` gives every order
  the adapter's front moves pass through from the start to the asked order
  (the adapter's rule copied, since its module needs the provider library,
  and held to `_to_the_front` by a test over every order of four). When the
  account stands in one of them, tracks added or taken off since left out of
  the comparison (`reached`), the merge is handed the account as the write
  would have left it had it finished (`finished`), and
  `pair_merge.merge(..., stopped=Stopped(...))` reads each side's change of
  order against what the stopped write left: rekordbox leads when it alone
  changed since, the account when it did, and otherwise the side that led the
  stopped write. Any other order is a move somebody made and leads as before.
- **Its additions and removals are not the person's, when it wrote both
  sides.** When the stopped write committed rekordbox, both bases are what it
  left: the account as its answered removals and additions left it, in the
  order it asked, and rekordbox as its commit did, with its moment as the
  base's. A track the write added and then taken off in rekordbox comes off
  the account rather than going back. When it skipped rekordbox neither base
  moves, since a base moved for one side alone reads the other side's
  removals as never made.
- **The gate names it.** The pair's line says it finishes run RUN's write,
  stopped part way through its order, and `sync-pair-finishing` names each
  such pair with its run. The pair's digest carries the run only when there is
  one. `docs/GUIDE.md` says what a DJ sees.
