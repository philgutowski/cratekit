**U248, #677, every crate command imports only the verb it runs, built in
the cloud lane on 2026-11-12.** Filed from the speed survey of 2026-11-12.
Medium: no path that writes or deletes, but it changes the parser every
command builds.

**The change.** `cli.build_parser` makes each verb's subparser from registry
data alone, the same `add_parser(name, help=summary)` call as before, and
imports nothing. Its subcommand actions are `_LazyChoices`, a subclass of
argparse's own: when argparse selects a word naming a verb, `__call__` imports
that entry's module and runs its builder on the subparser already listed under
that name (`_Unbuilt.build`), or makes it the stub on a missing extra; when a
help screen lists the children, `_get_subactions` asks each verb that declares
extras whether it is a stub, by importing it, once. argparse keeps every
decision about which word is the verb, so the global options, their values,
`--option=value`, abbreviations and `--` read exactly as before, and nothing
reads the command line of its own. `eager=True` keeps the old construction
loop verbatim, for the tree walk in `tests/test_docs_current.py`, for CI's cold
install, and as the oracle the parity tests hold the lazy tree to.

**Why the stub is still decided by the import.** The five entries that declare
extras (`analyze.run`, `calibrate`, `validate`, `restamp` on
`cratekit.analysis.cli`, `analyze.vocals` on `cratekit.vocals.cli`) all import
their extras inside functions, so on the real registry no stub line appears
today, extras installed or blocked. A `find_spec` over `extras_modules`, the
brief's suggestion, would have printed five stub lines the eager parser does
not, so the brief's own condition ("check first ... so no stub appears or
disappears") ruled it out.

**What changed on purpose.** A defect in one verb's own module no longer stops
`crate` building its parser: it fails loudly, as itself and never as a missing
extra, when that verb is selected, and a help listing that would have asked it
shows its plain summary. An `argparse.ArgumentError` from a verb module's import
or builder leaves as a `RuntimeError` naming the verb (review rounds one and
two), because inside argparse's parse it would otherwise read as the user's
usage error. `test_a_defect_in_our_own_module_does_not_masquerade_as_a_missing_extra`
now drives the defect at selection and the eager parser's raise at construction.
