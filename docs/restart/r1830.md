**What landed.**

- **`core/rb_writer.py`, the renumbering.** `renumbered_positions`, pure:
  in each playlist a removed live row leaves, every surviving live row
  above it goes down by one per removed live row below it. That is the
  binding's own rule in `remove_from_playlist` (strictly above, down by one
  per removal), held to live rows. `removal_renumbering` reads every
  membership row of every playlist concerned from SQL, with its marker, and
  refuses a playlist holding a NULL marker as `soft_deleted` refuses one.
  `CollectionRemoval.prepare` reads it, `CollectionRemoval.renumbering`
  answers it for the plan, and `commit` writes it through
  `renumber_memberships`: one `UPDATE ... SET TrackNo` per row from SQL,
  naming the number it was planned from, so a row that moved refuses, inside
  the removal's transaction and before the confinement. No `updated_at`, no
  `rb_local_usn` and no counter step is written for a renumbered row, which
  is what rekordbox wrote. `DatabaseReading.positions` keeps each membership
  row's playlist, content row, `TrackNo`, marker and a digest of its other
  columns; `collection_removal_violations` admits a changed membership row
  only when the rule renumbers it, to exactly the rule's number, with
  nothing else moved, and refuses a planned renumbering that was not made.
  The session record names each renumbered row, from and to, only when
  there is one.
- **`sync/removed.py` and `sync/removed_cli.py`.** `RemovedPlan.renumbered`,
  the count, in the digest, so a count that moved between the gate and the
  write refuses as `decision-stale`; the gate's screen and the payload's
  totals show `memberships renumbered`, the writes line says it, and the
  applied message counts it. `Removed.renumbered` carries it out.

**Decisions, recorded.** The binding's `remove_from_playlist` is not
reused, against the brief's approach line, because it commits by itself
and stamps `updated_at` and `rb_local_usn` on every row it moves (its
`on_move`), which is not what rekordbox wrote; its numbering rule is kept.
The `TrackNo` write is from SQL, because an ORM write adds `updated_at`
through the binding's `onupdate`; the whitelist would have admitted the
column, and the SQL confinement judges every row, and a source guard holds
the write to its one caller. "Otherwise unchanged" in the sitting's
measurement is read as every column but `TrackNo`; the attended card reads
the renumbered row's every column again. History lists are left as they
are, as the brief says, and any history row moving is still refused.
A row marked removed is neither counted nor moved (round one's B1), so a
playlist the track was only marked out of is not renumbered. A gap an
earlier removal left stays a gap. The plan asks `CollectionRemoval` rather
than a new module function, which keeps the feature packages at the
ceiling of 446 core names (the battery read 447 at first).
