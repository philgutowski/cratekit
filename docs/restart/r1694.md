**What failed, measured on the base.** `provider_session._login` (U261) wrote
the client's refresh back at its scope's close and nothing caught a refusal of
that write. On the product's own opt in for a machine with no keychain,
`CRATE_ALLOW_ENV_CREDENTIALS=1` with the session in
`CRATEKIT_CREDENTIAL_PROVIDER_SESSION` and keyring's fail backend, a login
whose client refreshed raised `CredentialBackendUnavailable` out of
`client_session`, and `label harvest` answered `internal-error` with
`report-defect` where it answers `label-playlist-unreadable` without the
refresh. Every verb that opens the catalogue or the account was blocked for a
person on the opt in once the stored access token had expired.

**What landed.**
- `materialised_session` takes an optional `unstored` callback. When given,
  a write back at the close that failed with one of `STORE_FAILURES`
  (`secrets.CredentialError`, `CratekitError`, `OSError`: the keychain's
  refusal and the index's lock, the index's unreadable refusal, a file the
  write could not make) is handed to it instead of raised. Only the write
  back is inside that catch: what the body raises, a provider's rejection, a
  gate's refusal, an unreachable login, is thrown at the `yield` and never
  reaches it. Without the callback nothing changes, so streamrip's scope
  raises as before and the drive keeps its own catch.
- `_login` passes it. A login whose client refreshed goes on with the logged
  in client and returns the session it read as the one the keychain holds,
  so `session_for`'s reuse compares the keychain against what it really
  holds and the next resolve reuses the client rather than logging in and
  failing to store again. The token file is rewritten only for a changed
  session, so a file that cannot be written is never reported over a
  session with nothing to store; a field the file cannot encode is still a
  defect and raises. The failure's class, never its words, is noted
  (`provider_session.unstored()`, process wide).
- The dispatcher reads the notes before and after every verb, off the module
  only when something loaded it as the ISRC count is, and adds one
  `provider-session-not-stored` warning on every branch, refusals included:
  the session the login refreshed could not be stored (the classes, each
  once), so the next run logs in again from the stored session.
- The literal moved to `provider_session.SESSION_NOT_STORED`;
  `vendored.SESSION_NOT_STORED` aliases it and `vendored.drive` catches
  `provider_session.STORE_FAILURES`, the same three classes it caught. The
  drive's warning words no longer say the stored session is left as it was,
  which was false when only the index refused after the keychain took the
  refresh (U274's words, corrected here since the branch edits the file).

**Kept.** A rejected session (a 401 or 403 at the login) and an expired one
