**R-1313, #561, a 404 whose body is not JSON is read as not found by the
account, the catalogue, the ISRC cache and the acquisition adapter, built in
the cloud lane on 2026-11-06.** The sibling of R-1305 on a different status.
Sized large by METHOD's rule though small in lines: the readers decide what
the ISRC cache keeps for a week and what a release read answers as gone.

**What the defect was.** Measured first on tidalapi 0.8.11's own request
handler through `tests/provider_answers.client_failure`: a 404 whose body is a
page surfaces as `requests.JSONDecodeError`, context the standard library's
decode error, then `StopIteration`, then the `HTTPError` carrying 404, three
context links down and no declared cause. A 404 with an empty or a JSON body
is `ObjectNotFound` raised from the `HTTPError` and always read right.
`adapter.classify_unavailable` (and so the outbound account's `_not_found`,
which asks it), `isrc_cache.said_not_found` and the catalogue's `_gone` read
the failure alone, so a track or release the provider had nothing for was
retried, failed as `unavailable-transient` and asked again every run. Driven
first on `main` by this unit's tests (`ded15d9d`): thirteen failed.

**What landed.**

- R-1305's walk, `failure_links`, and `answered_status` move from
  `acquire/provider_session.py` to `core/cause.py`, beside `_chain`, because
  the adapter's classifier now reads them and the login module imports the
  adapter. `provider_session` imports them under the same names, so the
  outbound account and R-1305's tests are unchanged.
- `core.cause.nearest_status`: the status on the FIRST link the walk reaches
  that carries one, and `answered_not_found` when that status is 404. Nearest,
  not any, so a server error met while handling a not found is the outage it
  says and is never kept as an answer. The walk's refusal limit already keeps
  a 404 under a product refusal that was only being handled out.
- The four readers read the status through it; class names and text are still
  read off the failure alone. `NoFileLanded` is still asked first in the
  classifier, since it is raised from the cause it carries (R-703).
- Round one's fix: off the declared chain the walk takes a link's own cause
  before what it was raised while handling, as its docstring said of the
  declared chain, so a wrapper raised from a 404 while a 503 was handled is
  read as the 404.
- `tests/test_provider_not_found_bodies.py`, 56 tests: for each reader, a 404
  with a page, an empty body and JSON is a not found; a 503, 502 and 500 with
  each body is not; a 503 page met while handling a 404 is not; a failure met
  while handling a refusal raised from a 404 is not; a rewrapped 404 page is;
  a cyclic chain ends; a not found class reached only as context is not; the
  nearest status read and the walk's order off the chain. Through the seams:
  an ISRC answered by a 404 page is asked once and kept at the account and the
  catalogue, a 503 page is retried and never kept; a release answered by a 404
  page is gone at once with one read, a 503 page climbs the ladder; a track
  answered by a 404 page is permanent with no retry remedy, a 503 page
  transient; a `NoFileLanded` carrying a 404 page stays transient.
- `docs/GUIDE.md` says what a person sees, after R-1305's paragraph. The 429
  solutions entry names the nearest status rule, where the walk now lives, and
  the trap of raising an already raised failure inside a handler.

**Decided, not asked (code).** Names stay read on the failure alone rather
than on the declared chain the brief allows: no reader needs the widening, and
a declared `FileNotFoundError` under a wrapper would otherwise read as a gone
release in the catalogue. The walk moved to `core.cause` rather than the
adapter importing it lazily from the login module. A test helper that raises
a failure inside a handler returns one the client already raised as it came,
since raising it again there rewrites its context (found building the tests,
now in the solutions entry).
