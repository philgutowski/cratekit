**R-1844, #926, `crate delete review` offers a landed track removed in
rekordbox even after Phillip deleted the playlist its landing made, built in
the cloud lane on 2026-11-22.** A large card, since it widens which files a
deleting path offers for the Trash. It was filed from A200 (#922) at sitting
102, which measured that rekordbox 7.2.19 deletes a playlist outright when a
person deletes it in the sidebar: no `rb_local_deleted` marker, and its
memberships and cloud filter row go with it. R-1037's guard read a landing
whose made playlists were all gone as rolled back, so the most ordinary tidy
up stopped every later removal of that landing from being offered.

**The fact chosen.** A landing stands, and is not rolled back, when the
database holds **one of the landing's own rows, live or marked, under the UUID
the landing recorded for it**, or, as before, every playlist the landing made.
The content id is random (`generate_unused_id`) and the UUID a fresh `uuid4`
the landing wrote, so no database from before the landing holds the pair,
whatever put it back: `restore run`, a bare metal recovery or a hand copy. The
id alone is not enough, since an import after a rollback can draw the same
random id. A playlist deletion (A200) and Remove from Collection (A178, A185)
leave the landing's other rows untouched. The playlist proof stays, so a one
track landing whose playlist is kept is still offered (A129's case).

**What landed.**

- **`intake/native.py`.** Each landed row on the `collection_landed` record
  now carries its `uuid` beside its eight columns, read back after the commit
  (`LANDED_UUID_KEY`, spelled again in `deletion.library` and held equal by a
  test). Records written before this card name no UUID, so only the playlist
  proof applies to them.
- **`deletion/library.py`.**
  - `read_collection` keeps every row's UUID, live or marked, from the same
    single walk (`CollectionRead.uuids`, read only).
  - `_landing_stands` holds the two proofs.
  - `landed_absences` returns a `LandedRead`: the absences, plus for each
    landing read as rolled back the ids of its absent rows. A landing with no
    absent row is neither weighed nor listed.
- **`deletion/run.py`.** `plan` passes the UUIDs in and sets `Plan.rolled_back`
  to `LandedRead.unasked(mark.absent)`: the rolled back landings holding an
  absent row that no run numbered, that is, one never offered and never taken
  as history.
- **`deletion/cli.py`.** The gate's screen shows `landings read as rolled
  back: N` whenever N is not zero, the way U243's ignored count is shown.
  `_plan_digest` does not read it.

**Decisions, recorded.**
- The fact, as above. The brief offered the landing's content rows or the
  database identity and counter; the counter was driven to failure by R-1037's
  review, so the rows it is, under their UUIDs.
- The count leaves out a landing whose every absent row a run already
  numbered (round one's SHOULD-FIX). Otherwise it grows with every batch
  tidied after its removals were offered, until it says nothing.

  names. The tests are in R-1037's file, `tests/test_delete_landed_removed.py`.
