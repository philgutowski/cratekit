**R-1665, #804, a capture of a database in write ahead log mode is one the
restore can use, built in the cloud lane on 2026-11-13.** Filed at the review
of #701 (U272). Large by METHOD: it changes the capture every guarded write
takes its restore point on.

**What failed, reproduced on the base.** `snapshot.capture` records which of
the engine's companion files landed by looking at the capture directory, then
runs `rb_writer.integrity_ok`, which opened the capture itself through the
binding. Its connection was the only one the capture ever had, so its close
was the last close of a WAL database: SQLite folded the log into the captured
database and deleted the captured `-wal` and `-shm`, which the manifest
already listed. `restore.plan` asks `snapshot.assert_sources_present` and
refused the capture as recording two files it no longer holds. It needs only
a log file present at the copy, which any WAL database has while a handle is
open; the caller's own `wal_checkpoint(TRUNCATE)` truncates the log and leaves
the file, so the ordinary call shape hit it too. Every capture test used a
stand in verifier that opens nothing, which is why the suite never saw it.
The tests written first, `tests/test_snapshot_wal_r1665.py`, drive it on the
suite's real disposable database, built in WAL mode because the real library
runs in it, with the real check: 12 of 15 red on the base.

**What landed, two layers, guard first.**
1. **`snapshot.capture` never records verified over what the check changed.**
   It walks the capture before the check and again after it (`_walked`,
   derived by walking as `_harden` and `_flush` are, raising on a directory it
   cannot read) and the verdict counts only when every file is still there at
   the size and modification time it was copied with and every directory
   still exists (`_changed_by_the_check`). A walk that fails on either side
   leaves no verdict. What a check adds is in no record and is not asked
   about; the flush after the check still covers it.
2. **`rb_writer.integrity_ok` never opens the file it is given.** It copies
   the file set through `disposable_copy`, the one loop the capture uses
   (`_copy_file_set`, its companions derived from the state schema), into a
   private temporary directory, checks the copy, and removes it. The verdict
   is about exactly the given bytes, log included; the close folds and deletes
   only the copy's log. A copy that cannot be made answers False with a log
   warning. The rehearsal's own check of its scratch database in
   `intake/land_cli.py` no longer changes that database either; nothing reads
   it after the check.

**Unchanged:** what is copied, what is checked (the same bytes, log
included), every refusal (`assert_verified`, `assert_sources_present`), U272's
flush and its order (check, then flush, then manifest, then the directory
flush), the verifier seam. **Decided here, recorded:** the throwaway copy goes
in the system's temporary directory, as `disposable_copy` already does for
every read only diagnostic, rather than in the capture store, where a crash
would leave a directory every reader of the store meets; its room is a
residual below. Fixing the check in `integrity_ok` rather than in
`snapshot._verify` fixes every caller and leaves the verifier seam the tests
drive unchanged. Code conventions were the session's to decide.
