**U209, #499, answering a gate does not replan the whole sync, so a two gate
sync pair costs one plan of provider calls, built in the cloud lane on
2026-11-05.** A large card: it moves the guard in front of `crate sync pair`'s
writes to the rekordbox database and the account from the gates' digest to a
check of the lists the plan read.

**What landed.** `core/held_plan.py` holds a run's plan between the commands
that answer its explicit gates, in a new declared state directory
`held_plans` (`runs-held`, installation scoped, never restored), one file per
run, owner only. The plan's dataclasses are written as tagged JSON and read
back only through a closed registry of classes the verb names, never imported
by name and never unpickled, and a plan is held only when it reads back equal
to itself. `load` answers the plan or why not: no file, another version, kind
or run, a file that does not decode, one that digests other than the digest
held beside it, or one older than thirty days; a held plan older than that is
also pruned when a new one is held, and a run's plan is released when the run
writes or stops with nothing to write.

In `sync/pair_cli.py`, the command that plans holds its plan with the pairs it
was asked for and the calls its plan took. A later command of the run, a
`run decide --continue` or the verb run again with `--run`, reads the plan
back only when it digests to every offer the run recorded and was made for
the pairs this command asks for; otherwise it plans again, digest bound, and
says why on the gate screen (`planned again`) and in the answer
(`sync-pair-replanned`). So the second gate and the write use the plan the
person was shown, and a two gate sync makes one plan's lookups.

Before the first write of a held plan, `check` reads only what the writes are
made from, for every pair whichever gate applied, since each side's writes
were merged from both: each rekordbox membership and each account listing
(its order and its withheld count), the rows a pair adds, the place of a
playlist the product pairs by itself as discovery and `home_of` read it now,
whether a made pair or a pair let go for its rekordbox side still sits where
it sat, a made account side's folder (still there, free of a playlist of its
title, or not yet made by hand), a brought playlist's folder and title on the
account, and the acquisitions another sync queued since the plan. It never
matches a track. Anything moved refuses `decision-stale` before any pair is
written, naming every moved list in the message and in `detail.moved`, and
the held plan stays so the run says stale again. A pair with nothing to write
on the account records the listing the check read as its snapshot rather
than listing again. The answer carries `totals.calls` with `plan`, `check`
and `write`, read from the provider gate's own process count around each
phase, the plan's count held with the plan, and names them on its message
line.

**Decided, recorded here.** The held plan is a file beside the run records
and not a field of them, because every reader of a run record (`run show`,
doctor's scans, the sibling warning) would read the whole plan, and because
the run directory's files are each read as a run. JSON through a closed
registry rather than pickle, so a held file can build nothing the verb did not
list. A plan that cannot be held, or read back, costs a plan and never a
write: the gates still compare. The check covers every pair, not only the
side applied. A no change sync still lists each pair once at the check and
records its snapshot, rather than stopping after its plan, because a pair
whose first sync never completed would otherwise stay first (filed). The
calls are inside `totals`, since `plan/1` is closed.
