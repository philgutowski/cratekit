**U212, #506, a sync pass does not download again a track an earlier unlanded
pass already staged, built in the cloud lane on 2026-11-05.** A large card: it
changes what a sync pass downloads and when it ends, across the missing list,
the pass, the naming verb and the tail, though it adds no path that writes or
deletes.

**What sent it.** Sitting 55 (A70) ran `crate sync land` over an account that
still had two tracks an earlier pass had downloaded, tagged and named in the
download staging folder, the earlier pass's landing gate never answered. The
pass downloaded them again, the new copies took names for their provider ids,
and `name apply` refused `rename-incomplete` with "already taken in the folder
by a file nothing here is renaming", which sent the session to compare audio by
hand.

**What landed.**

- `intake missing` reads the ISRC the downloader writes on every file it
  delivers from each file in the staging folder, through the reader the landing
  uses (`match.index_paths` over `landing.listing`), and a missing track a
  staged file carries is counted as staged and not listed. The summary carries
  `staged`, `staging` and `staged_tracks`, and a `staged` row says what was
  skipped and that the landing over that folder lands it.
- An unreadable identity is never a match: a row with no ISRC, a staged file
  with no ISRC tag or one no reader opens, are not the track.
- A row this list's own earlier copy names, by provider id or by ISRC, is never
  subtracted, so a continued pass reads its own downloads and writes the same
  list byte for byte rather than refusing over its earlier copy.
- A staging folder that is not there is nothing staged, said. One that cannot
  be read fails the row and subtracts nothing.
- Every missing track staged is something to land, not a no op: the verb
  answers ok with no list, and `crate sync land` downloads nothing and lands
  what is staged. A download that lands nothing still lands what the pass
  staged. The pass's missing row says how many it skipped.
- The left out refusal over a run with a failed job stands aside when the
  finished jobs' only missing tracks are staged, and the skipped row still fails
  and names the job.
- `name apply` says a file held back by a name a file carrying the same ISRC
  holds is a second copy of one recording, in the plan, in the refusal and in
  the claim after the gate, and carries the ISRC on the owed item. A collision
  between two movers carries none.
- The pass's name step reads each such ISRC against this library's download
  jobs, earliest first, finished items only, and names every pass that
  downloaded it. With no such job it says the copy in the way did not come from
  a download here.
- The ISRC fold moved from `acquire/match.py` to `core/tags.py`, re exported
  from `match`, so the write layer reads it without importing a module above
  it. The earlier pass lookup lives in `cli/tail.py` for the same reason.
- `docs/GUIDE.md` and the intake and name skill say what a staged track and a
  second copy do.

**Decided, recorded here.** A staged track is known by its ISRC alone. The
brief named the provider identity, and the downloader writes the ISRC on every
file it delivers but no provider id, so a file renamed by an earlier pass's
name step carries nothing else to read. Matching by artist and title was
refused, since two releases of one title are not one recording. The cost is a
residual.
