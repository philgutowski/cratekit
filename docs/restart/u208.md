**What landed.** `sync/pair_cli._ask` asks the account seam with
`any_agreeing`, so a row whose ISRC names several releases that all agree
with it is matched exactly as the mirror matches it (R-1032): the hearted one
if the account hearts one, else the lowest numbered after the account's
several hearts or the file's album narrowed them. The refusals before the tie
are unchanged: no agreeing release, no row to judge agreement by, a candidate
that could not be read, and the last is still never remembered. The chosen
release is a match like any other, recorded as the pair's link at the apply,
so no later sync asks the provider about it. A miss remembered with the tie's
words before U208 is asked again and, matched, forgotten. This reverses
U198's rule that the pairs keep R-572's refusal; the hearts keep it.

The account seam gains one read only member, `tie_broken(identity)`, true
only when `any_agreeing` chose a release that without it would have been
refused, so a lone release, a lone heart or an album naming exactly one is
never a broken tie. The gate counts broken ties per pair on the pair's facts
line ("N row(s) matched as one of several releases that all agree with it"),
in `totals.tied`, and as `tied: true` on the account add it chose.

The reverse direction. An account track the library lacks whose ISRC no
row's database ISRC names is looked for among the pair's own rows, by
database ISRC or else the row's file (`here` in `_owned`), before intake jobs
and landings, so a release of a paired row added by hand on the account maps
to that row and is never queued for download.

**One row, one key.** The review's two rounds drove that a row linked to two
account releases (the tie's pick plus a sibling added by hand) was two keys
in the merge, so a row removed in rekordbox came back on every sync and a
sibling taken off the account rewrote the row and came back. `plan_pair` now
reads every account release linked to a row as that row's one key, the
lowest numbered linked release's, through an alias map frozen before the
merge: a removal on either side takes every release of the row, one release
taken off the account while another stays keeps the row (at the remaining
release's place, since the order follows the account), and the account order
compares the keys' first occurrences, so a release the person places is not
moved. When the account already holds two or more unlinked releases of a
row's ISRC, the lowest of those is taken, never a release the provider names
that the account lacks. The same rule now applies to pairs that already held
two links to one row on main through the database ISRC path.

**Decided, recorded here.** The tie flag is a protocol member rather than a
reason string, since `StrictAccount` refuses anything outside the protocol and
the reason is defined as empty after a match. The count sits on the facts
line and in totals, outside the digest, so the three plans one sync makes
digest alike. Within one sync an unlinked tie is still asked once per plan,
as every unlinked match is, until the apply records the link; a per sync
cache of answered ISRCs is U206's.
