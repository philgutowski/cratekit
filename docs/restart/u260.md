**U260, #689, an album's one cover is fetched and encoded once in a `tag
folder` sweep, not once per track, built in the cloud lane on 2026-11-12.**
Filed from the speed survey of 2026-11-12. Taken as large: the write path is
unchanged, but what `write_front_cover` is handed comes from memory for the
second file of an album on, so any change in what a file carries was held as
a merge blocker.

**The change.** `searchers.for_images()` is one fetch per process, the per
process binder the solutions entry on queued workers prescribes, like
`published.for_lookup`. It wraps the shipped paced `default_image_fetch()` in
`searchers.remembering(..., admit=art.decodes)`: a memory of the bytes the last
`IMAGE_MEMORY` (4) addresses answered, keyed on the address exactly as named,
least recently used dropped first. A fetch that raises, answers None or empty
bytes, or answers bytes that do not decode in full is never remembered, so the
next file asks again as before. The pacer is untouched and still waits before
every request that is made; a remembered answer makes no request.
`art.to_cdj_jpeg_remembered` keeps the last `COVER_MEMORY` (4) encodes, keyed
on a SHA 256 digest of every byte, the length, the edge and the byte cap,
never the address, and never remembers an `ArtError`. `_art_embedded` calls
it; `to_cdj_jpeg`, the repair path and `write_front_cover` are unchanged, and
the writer still measures every file's bytes. `searchers.reset_images()` and
`art.reset_cache()` drop the memories, and a new autouse fixture in
`tests/conftest.py` calls both around every test. `tagging/cli.py` `handle`
is unchanged: it still asks the binder per item, which now hands back the
shared fetch.

**Measured.** The card's reproduction, driven through the binder the worker
calls per file: ten files of one album make 1 fetch, 1 encode and 1 pacer
wait, against 10, 10 and 10 before. Review round one ran a differential sweep
of 53 files over .flac, .mp3, .m4a, .aiff and .wav, 18 addresses and every
failure shape (a 503, a transport error, three 429s, an empty 200, HTML, a
truncated JPEG, each then good) against the base's own source: every file's
whole hash, result and sentence identical, 55 requests down to 35, pacer
waits equal to requests and each at least 1.0 s. The extra full decode the
admission costs per real request was measured at 16 ms for a 1400 px source.

**Decided by the session, recorded here.** Bytes that do not decode are not
remembered, so a cover that fails to decode for one file is asked for again
by the next, exactly as before, at the price of one decode per real request.
Four entries in each memory: a sweep walks sorted paths, so an album's files
usually sit together, and a folder interleaving more than four albums asks
once per file as before, never more. Nothing is kept across processes; a
detached resume is a fresh process (R-226). The memories hold no lock across
a fetch, since a sweep claims its items in one serial loop. The test layout
(one new file, `tests/test_album_cover_once.py`, plus one verb test) was the
session's to decide.
