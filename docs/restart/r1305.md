**R-1305, #557, a rejected session whose answer body is not JSON is told to
sign in again rather than told the provider is unavailable, built in the cloud
lane on 2026-11-05.** A small card: the change picks a refusal's reason and
remedy, and whether the held account is forgotten, and writes nothing. The
mutation table is sized to a unit that writes, as the brief asks.

**What the defect was.** Measured first on tidalapi 0.8.11's own request
handler over a canned `requests.Response`: a 401 or 403 whose body is a page
surfaces as `requests.JSONDecodeError`, whose context is the standard
library's decode error, then `StopIteration`, then the `HTTPError` that carries
the status, three context links down and no declared cause anywhere. A 401
with an empty or a JSON body re-raises the bare `HTTPError` and always read
right. `provider_session._rejected` (the login) and
`account._session_refused` (a call after login) walked declared causes only,
so the page case read as `unavailable-transient` and the held account was
kept. Driven first on `main` by this unit's tests (`1f7994a3`): eleven failed.

**What landed.**

- `provider_session.failure_links`, the one walk both readers use: the failure
  and every error it was raised from or raised while handling, once each, the
  declared chain first and marked so. It departs from `core.cause._chain` for
  the reason above, with two limits that keep `_chain`'s reason for not
  reading context: off the declared chain it never enters a `CratekitError`,
  so an outage met while handling a refused session is still a wait; and a
  reader trusts a link reached only as context for its status, never for its
  type or name, as `label.sweep` reads a 429 (R-704). A `walked` set ends a
  cycle on either link; the old cause walks had none.
- `_rejected` and `_session_refused` read a status on any link it yields, and
  the client's `AuthenticationError` by name only on the declared chain.
  `answered_status` reads the status.
- `tests/provider_answers.client_failure` builds each failure by driving the
  installed client's handler, and `tests/test_provider_rejection_bodies.py`
  holds 33 tests: 401, 403 (and 400 at login) with a page, an empty body and
  JSON read as rejected in both places; 500, 502 and 503 with each body still a
  wait; a cyclic chain ends; an outage met while handling a rejected session's
  refusal, raised from its 401, is a wait; an `AuthenticationError` reached
  only as context is a wait; a rewrapped page is rejected; and the walk's
  order. A held account is dropped on a page answering 401 and kept on a 503.
- `docs/GUIDE.md` says what a person sees, after the sign in paragraph. The
  429 solutions entry now names this walk and the test helper.

**Decided, not asked (code).** One walk in `provider_session.py` rather than a
copy in each reader, since the outbound account already imports from it. The
cycle tests count their own link reads (a `Looping` failure that raises once
past a bound) rather than run the walk on a thread with a time limit: a thread
left spinning inside `materialised_session` held up every later test in the
file. `_stale_tag` in `tidal_account.py` keeps its own walk, which follows
both links with no refusal limit; it reads only a 412, which no refusal of
the product carries, so it was left as U220 built it.
