**R-1017 built, 2026-10-14, on `relay/323`, issue #323: `crate export set
--rename JOB` finds the set's account playlist by the name its landing
recorded.** The Signal set's job has no frozen name, its page words spell
neither the landing's name nor the new one, and a backfill made its account
playlist under the name the landing wrote, so the rename refused it as
`export-set-rename-unresolved`.

- `set_playlist.recorded_names(cfg, job_id)` reads the names every landing
  of the job recorded under the `set_playlist` detail, newest first, from
  closed records whose source committed. It shares one filter, `_landed`,
  with `recorded_playlist`, which still wants the live row; the name is read
  whether or not the row is still there, since the account playlist's name
  outlives it.
- `set_cli.plan_rename` looks the ledger up under the frozen name first,
  then the recorded names, then `_names_for_job`. The refusal names them all.
- **From the review round,** `sets.plan_rename` reads every name rather than
  stopping at the first that holds a record, so two different playlists
  under two of the set's names refuse as a twin, as one under the new name
  beside an older one already did. The twin refusal names the held playlist
  under the key it is recorded under.
- **Planning's call.** The brief also names the account identifier the
  landing recorded. No landing record carries the account playlist's
  identifier in this tree (the detail's `id` is the rekordbox row, and the
  ledger's `sets` entries carry no job), so resolution is by the recorded
  name alone. Filed unnumbered as `docs/residuals/r1017-a-...`.
- Not changed, from the review: `_job_for_inspiration_name` still scans the
  session log for a name with no closed or committed filter, the backfill's
  own lookup and outside this brief; `plan_rename` now parses the session
  log twice, once in `_inspiration_of` and once in `recorded_names`.
