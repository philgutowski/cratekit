**R-1264, #532, `crate sync pair` reads each pair's account side row by row,
so one track the account lists with no title or no artist never stops a pair,
built in the cloud lane on 2026-11-05.** A large card: it changes what `crate
sync pair` writes, since a pair that refused now syncs.

**What the defect was.** `sync/pair_cli.py` `plan_pair` listed each pair's
account side through `intake_cli.list_playlist_dated`, whose reader refused the
whole playlist with `intake-list-unusable` when one row named no title or no
artist. A sync of every pair passed over a pair only for `sync-pair-unknown`
and `sync-pair-out-of-scope`, so that refusal stopped the run and no pair
synced. U213 made it more reachable: `crate sync twins` now makes a twin over
such a playlist and records the untitled track in its snapshot, and the next
pair sync stopped. Driven first on `main` by the residual's own driver: seven
of the eight first tests refused `intake-list-unusable`.

**What landed.**

- `plan_pair` lists through `list_playlist_readable` (U213's row by row
  reader), which now also gives the added dates (`_added_dates`, shared);
  `list_playlist_dated` lost its last caller and is removed. A track the reader
  refuses is **unread**, kept by its id: never added to rekordbox, never read as
  taken off the account (its key is stripped from the base, so a row linked to
  it stays), never offered to the account, and a rekordbox row carrying its
  ISRC matches it rather than asking the provider for another release.
- The pair otherwise syncs whole: removals land on both sides, the snapshot
  moves with each unread id in its place (the check's listing order when the
  account takes no write, the provider's listing after one), the account's keys
  are read in listing order, each at its first release's place whether that
  release reads or not, and an account reorder is computed over every listed id
  and written whole, each unread track kept behind the one listed before it
  (`_with_unread_placed`).
- The gate names each unread track: warning `sync-pair-unread`, an item
  `account / unread`, a `totals.unread` count and a line in the pair's facts.
  The digest carries the unread ids only when any, so every other plan digests
  as before. `check` before the write reads the same way and refuses
  `decision-stale` when the unread set moved; places alone are not a move.
- `PER_PAIR_REASONS` takes `intake-list-unusable`, which the row by row reader
  still raises for a row with no provider id: a sync of every pair leaves that
  pair out by name and syncs the others; a pair named alone refuses as itself.
  A refusal not about one pair, an expired session, still stops the run.
- `docs/GUIDE.md`, under the custom playlist twins.

**Decided, not asked.** "A pair named alone keeps its behaviour" is read as:
the per pair leave out applies only to a sync of every pair, while the row by
row read applies however the pair is asked, since the goal's second half asks
for it. A playlist brought from a synced folder (U202) is read the same way,
so one with an unread track is now made in rekordbox with its readable tracks
rather than listed. `label-playlist-unreadable` stays out of the per pair set,
as the brief names only the reader's refusal.

**Reviewed by Fable at high effort, two rounds, both fix rounds spent.**

- Round one, on `c0f46d1a`: one BLOCKING, five residual. BLOCKING, driven:
  the build held the snapshot back while a track was unread (the short listing

  Fix round one (`30b98201`) let the snapshot move and removals land, compared
  the unread tracks as a set, pinned the ISRC match against a provider naming

- Round two, on `30b98201` against `c0f46d1a`: two BLOCKING, three residual. The fix round's own:
  with the account reorder withheld while the snapshot moved, the next sync let

  round one did not reach: an unread release beside a readable one (U208)

  reordered with nobody moving a track. Fix round two (`c8ba4343`) reads the
