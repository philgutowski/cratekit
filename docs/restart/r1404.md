**R-1404, #608, a pair outside GIG READY reordered in rekordbox keeps
rekordbox's order sync after sync rather than having it put back to the
account's two syncs later, built in the cloud lane on 2026-11-07.** A large
card: it changes what `crate sync pair` writes into rekordbox. Filed by
R-1376's round two review (#597) and live on main since U231 (#595): a hand
pair of an account playlist 1, 2, 3 and a root rekordbox playlist 1, 2, 3,
rekordbox reordered to 3, 1, 2; the next sync answered `sync-pair-nothing`
and the one after wrote rekordbox 1, 2, 3 again with nothing said.

**What landed.**

- **A base whose two sides disagree on order keeps rekordbox's order**
  (`sync/pair_merge.merge`). A whole write always puts rekordbox in the
  merged order, so a snapshot whose rekordbox order disagrees with its
  account order, on the tracks both held, records an order that never crossed
  to the account. With no stopped write, rekordbox now leads when the account
  has not changed order since the base and either rekordbox changed order
  since it (as before) or the base's two sides disagree (new). The account
  still leads whenever it changed order since the base, and when both did.
  A base whose sides agree, which every pair whose account order is written
  holds after a whole write, plans exactly as before, the tie between two
  additions included.
- **General, not gated on `_keeps_order`.** The same snapshot is left by a
  rekordbox addition placed mid playlist on a pair whose account order is
  not kept (the account appends it), and by a pair whose scope changes after
  it diverged (moved under GIG READY, or `outbound.pair_order_every_pair`
  switched on); each put rekordbox's order back on main too, and each now
  keeps it, the second by writing rekordbox's order onto the account.
- `pair_merge`'s module docstring says the rule; `docs/GUIDE.md` says a
  rekordbox reorder made after the first sync stays until the playlist is
  reordered on Tidal, which brings Tidal's whole order.
