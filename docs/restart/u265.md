**The change** (`src/cratekit/acquire/match.py`). `_approximate` handed
`rapidfuzz` the scorer `token_sort_ratio`, which split and sorted both strings'
words again for every pair, so each library name was sorted once per wanted
row. `token_sort_ratio` is `ratio` over the two sorted strings, so the pass now
sorts each recording once and the wanted token once and calls the same
`process.extract` with `fuzz.ratio` over the sorted forms, same floor, same
limit, mapping each hit's position back to the unsorted recording.
`LibraryIndex.sorted_recordings()` keeps the recordings and their sorted words
together, position for position, built the first time the approximate pass
asks and kept for the life of the index in a non init, non compared, non repr
field set with `object.__setattr__`, the house idiom for a frozen slotted
dataclass (`Owned.members` does the same). Lazy rather than built with the
index, the builder's call, so a landing or a set build that never reaches the
approximate pass pays nothing. The scorer import stays inside the function,
and `APPROXIMATE_FLOOR`, `APPROXIMATE_LIMIT` and their tests are untouched.

**The split depends on the string's width**, found while building and filed in
`docs/solutions/integration-issues/rapidfuzz-splits-words-on-a-whitespace-set-that-depends-on-the-strings-width.md`.
rapidfuzz's compiled scorer splits a string whose characters are all below
U+0100 on Python's whitespace except U+0085 and U+00A0, and a wider string on
exactly Python's whitespace. The first helper, a split on Python whitespace
less those two, passed an ASCII scan of every code point; the whole matrix
proof over odd raw spellings then found 18,219 pairs whose float differed,
every one a raw unfolded string. `_sorted_words` now reads the widest
character first. `fold` leaves neither character in any recording token, so no
shipped answer was ever at risk, and the helper is held to the scorer on any
text anyway.
