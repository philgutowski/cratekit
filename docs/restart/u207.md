**U207, #497, many ISRCs are screened in a few requests, and a track found is
never fetched a second time, built in the cloud lane on 2026-11-05.** A medium
card: it adds no path that writes or deletes, and changes only how ISRC lookups
are asked.

**What the probe found.** No app credential existed in the container, so no live
request could be made. The probe was the provider's published OpenAPI document
for `openapi.tidal.com/v2`, version 1.10.224, filed in `docs/solutions/` as the
entry on the multi ISRC filter.

- `filter[isrc]` takes at most twenty codes.
- Given several, the API answers **one track per code** and pages nothing.
- `include` brings the artists and albums.
- `availability` is marked deprecated in favour of `usageRules`.

So the brief's batching closes as specified: a batch cannot answer a lookup.
One code is often filed under a single, an album cut and several compilations,
and a batch answer is the one release the provider picked, the positional
choice R-572 refused. What a batch can answer exactly is whether the catalogue
files anything under a code, and that is what landed.

**What landed.**

- `catalogue_api.AppCatalogue.isrcs_held` asks two to twenty well formed codes
  in one request and returns the codes the answer names.
- `acquire/isrc_screen.py` holds `Screen`, which groups a plan's codes into such
  batches and keeps every code no answer named.
- `TidalAccount.screen_isrcs` and `TidalCatalogue.screen_isrcs` are declared on
  the `RemoteAccount` and `Catalogue` protocols. A lookup of a screened absent
  code is then answered not found with no request. Every held code is still
  asked alone, so `_among` sees every release as before.
- The callers screen before their first lookup:
  - `sync pair`'s `plan_pair` leaves out a linked row, a code the account
    playlist already holds under any number of releases (since U208 took one
    of several), and a remembered miss. The remembered miss test is the one
    `_remembered_miss` that `_ask` uses.
  - The account mirror's `read` goes through `Matcher.screen`, which leaves out
    what `_settled` answers without a request, reads each row's identity once,
    and has the mirror's request count hold what the screen spent.
  - `intake missing` screens its askable codes.

Measured on fixtures through the real gate: fifty codes the catalogue files
nothing under cost three requests where they cost fifty. Twenty codes with five
held, each under three releases, cost six requests where they cost twenty, and
each held code still reached `_among` with its three releases.

**Classified, recorded here.** An absence is read only from an answer
attributed whole. These answers mark nothing in their batch:

- a track whose ISRC is missing or unreadable;
- a code nobody asked;
- a `next` link;
- an entry that is not a resource;
- a body with no list.

A batch that fails is left to each code's own lookup, so one bad answer is found
alone. Stops and pass throughs:

- A rate limit stops the screening for the run, and the gate has counted it.
- So do a rejected app credential and any other 4xx, since every code sent is
  well formed and the API is then refusing the form of the request.
- The gate's own park passes through.

What is never screened:

- Any client but the app catalogue. The account session's library has no batch
  form, so without the app no request is made and every lookup is as before.
- A code not spelled as its own fold.
- A lone code, since its own lookup costs the same.

**Decided, recorded here.** The brief's "no per result refetch" was already
true under the app client, U205 reading the names off `included`. This unit
pins it at the gate: five releases cost one read. The account fallback still
makes the client library's call plus one `track(id)` per release. It was not
moved, because that would mean a request of Cratekit's own on the live path
without a probe of what the account token's answer includes; a residual
records it. U206's ISRC cache (#496) was not on `main` when this landed. When
both are there, the screen's absence check should stay ahead of the cache read,
and a screened absence could be kept as a not found; neither branch does that
yet.
