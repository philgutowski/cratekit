**R-1411, #613, a write that finishes a stopped order is held to the order
the plan agreed on, whatever else it adds or removes, built in the cloud
lane on 2026-11-07.** A large card: it changes what the account order write
of `crate sync pair` will move from. Filed by R-1394's review (#604): the
plan finishes a stopped write only from an agreed reading at or past the
moves sent, but the write that followed planned its remaining moves from the
adapter's own fresh reading, checked by the tracks it holds, so a reading
that lagged the stopped moves seconds after a true one still had the moves
sent by position from it whenever the same write also added or removed.

**What landed.**

- **An order the caller agreed on** (`modules/outbound/tidal_account.py`,
  the protocol in `modules/outbound/service.py`). `order_tracks` and
  `_settled` take `agreed`. Beside the check of what the reading holds,
  every track of `agreed` the reading still holds must stand in its order
  (`_in_agreed_order`, read over the tracks both hold, each at its first
  place), while a track it does not name, one this command added, may stand
  anywhere and one it names that the reading no longer holds, one this
  command took off, is not asked. A reading that fails it is read again
  after a pause like any disagreeing reading and then refused `read-differs`
  with nothing moved, an order refusal, so the pair alone stops and R-1394's
  rank keeps the stopped write pending.
- **The finish passes the plan's own reading** (`_write_account` in
  `sync/pair_cli.py`). At every finish of a stopped order, whatever else the
  write adds or removes, `agreed` is `one.account_before`, the reading the
  plan judged the stopped write from and carries in the held plan, with its
  unread ids in place. Not the check's listing (round one's review): a
  continue's check judges what the playlist holds and not its order, so its
  listing can be the lag itself, and a plan made again in the writing
  command has no listing. `expect` is unchanged, and every existing refusal
  is kept. `agreed` is passed only when set, so a stand in for the adapter
  that does not take it is asked what it always was; the stand ins in the
  tests forward it, and the discovery suite's fake account records it.
- `docs/GUIDE.md` says the rest of a stopped order is sent only while Tidal
  still serves the order it agreed on, also when the same sync adds or takes
  off tracks.

**Decided, recorded here.** No product question: the card's behaviour is
the conservative one, nothing moved and the pair left pending. Questions of

check's listing as the agreed one (round one).
