**R-1289, #547, `crate sync all` reads each swept playlist row by row, so one
track the account lists with no title or no artist never leaves the whole
playlist out, built in the cloud lane on 2026-11-05.** A large card: it changes
what `crate sync all` queues and what `crate organize`'s `mirror-downloads`
step queues.

**What the defect was.** `sync/playlists.py` `plan` listed each playlist it
sweeps through `intake_cli.list_playlist_declared`, whose reader refused the
whole listing with `intake-list-unusable` when one row named no title or no
artist. The sweep took that refusal per playlist, so the run went on, but the
playlist was excluded as unreadable and none of its readable tracks was
queued. `organize/mirror_downloads.py` listed the same way, and the account
mirror reads playlists as ids only, so one untitled row on a mirrored playlist
named every wanted track on it "the provider could not list the playlist".
Driven first on `main` by this unit's own tests (`876b1093`): both unread
scenarios left `Warmup` out whole, and the mirror world planned nothing.

**What landed.**

- `plan` lists through `list_playlist_readable` (U213's row by row reader).
  The readable tracks are queued as before; each unread track is kept on
  `Sweep.unread` and in the summary block's new `unread` key, by playlist then
  track id, with the artist, title, ISRC and why the account gives. The short
  listing check (R-515) rides beside it unchanged.
- A playlist every track of which is unread is excluded `unreadable`, its
  message naming each track and why, and is offered again as any unreadable
  playlist is; it is never reported `empty`.
- `PER_PLAYLIST_REASONS` is unchanged: a row with no provider id still leaves
  its playlist out by name and the others queue, and any other refusal, an
  expired session, still stops the source.
- `sync/cli.py` adds the warning `sync-playlists-unread`, over queued
  playlists only, naming each unread track by playlist, id and why, and saying
  that once a playlist's intake job succeeds no later sync offers it again, so
  a named track is brought in by hand once the account names it.
- `mirror_downloads` reads row by row too: `listed` now returns a `Readable`,
  a wanted track the reader set aside is named `not queued` with the reader's
  why, and the playlist's other wanted tracks are queued.
- `docs/GUIDE.md`, under the sweep's `intake missing --run` paragraph and the
  mirror's downloads; the reserved literal pinned under `sync/cli.py`.

**Decided, not asked (code).** The block key `unread` and the warning code
`sync-playlists-unread` follow `withheld` and `sync-playlists-withheld`. The
mirror's injectable `listed` seam takes the `Readable` whole rather than a
tuple, so the step reads the same object the sweep does.

**Decided conservatively, asked on the card.** A playlist queued without its
unread tracks is recorded in the cursor when its job succeeds, as a short
listing already is, so no later sync offers it again, and `sync mark`
prefixes it as usual. The warning says so in those words. The question for
Phillip, posted on #547, offers holding such a playlist out of the cursor, or
carrying the unread tracks on the job so `crate intake missing` lists them.
