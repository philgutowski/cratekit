**U254, #683, `crate adopt apply` records each applied entry by appending one
synced line to its ledger rather than rewriting the whole ledger, built in the
cloud lane on 2026-11-12.** Filed from the speed survey of 2026-11-12. Built on
scratch configurations and fakes only; the timed rehearsal on a copy is owed
(below).

**The journal.** The applied ledger, `adoption_ledger.json` in the library's
coupled state, the same file and the same inventory entry, is now a journal at
schema 2: a header line, `{"format": "journal", "schema_version": 2}`, then one
record per line, the fields `AppliedEntry.to_json` always wrote.
`apply.mark_applied` checks the record by the reader's own field rules, takes
the same exclusive lock as before, and appends the line through the new
`config.append_durable_bytes`, which refuses outside the test root like every
state writer, never creates a file, loops over a short `os.write`, and fsyncs
before it returns. The file is rewritten whole, through `atomic_write_bytes`,
only to create it, to turn a schema 1 document into a journal at its first
mark, and to cut a torn last line away. A capture and a restore copy the file
as bytes, so they carry it whole unchanged (driven by the review: nothing under
`session`, `restore`, `snapshot` or `rehearsal` parses it).

**The read, decided.** A file whose first line is not a journal header is the
schema 1 document every earlier build wrote, read by exactly its old rules and
refusals. In a journal only the last line may be torn, because each append is
synced under the lock before the loop touches the next entry; **a torn last
line, unterminated or not JSON, is read as the mark that did not finish**, the
documented crash between the tag write and the applied record, which the
resume re-applies without refreshing the revert record. Every whole record
before it stands, so a torn tail never reads as an empty ledger. Damage
anywhere else, a damaged header, a newer header (upgrade), a record failing the
field rules, and two damaged lines at the end all refuse as before. A re-mark
in a journal is folded last one wins, which is what the document's writer did.

**Linear CPU too.** A mark skips the whole read only when `os.stat` shows the
file exactly as this process left it, device, inode, size and modification
time; anything another process, a restore or an edit changed is read and
validated whole before a byte is appended, as every mark was before. Each of
the size, inode and time has a test of its own. `mark_applied` now returns the
path rather than the whole ledger, which nothing read. The loop's already
applied list uses the identifier set rather than a scan per entry.

**Measured.** The card's own reproduction on this container: 2,000 marks wrote
502,626,495 bytes in 18.95 s of CPU on `main` (`fc0e5cd3`), and write 384,933
bytes in 0.22 s on the branch; 250, 500 and 1,000 marks write 47,933, 95,933
and 191,933 bytes, the file's size, one record each. The test the card names:
400 marks write under 2.5 times what 200 do, the total equals the file's size,
and N marks make exactly one rewrite.

**A behaviour change, an improvement, recorded.** A record the reader would
refuse (an empty entry, tree, content or actor) is now refused before it is
written, with the ledger left as it was. Before U254 it was written and the
next mark, and every later read, refused the whole ledger. A rekordbox content
id is never empty, so no real input was found that reaches it.

**R-286 and R-230.** The same remedy fits R-286's restamp undo log, which only
ever adds an entry per item. R-230's outbound ledger keeps a per playlist
`added` array, which an append fits only as event records folded per playlist,
and its other half, a remote listing per track, an append does not touch. Both
are left to their own cards. The revert ledger written in the same loop, by
`revert.write_tag_with_record`, is quadratic too and was measured here (582
bytes a record, four times the bytes for twice the records); it changes its
records in place, so it is a residual and not this card.
