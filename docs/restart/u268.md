**U268, #697, the cloud battery reads and compares every failing id whole,
built in the cloud lane on 2026-11-12.** Filed the same day from the speed
survey of `main` as a latent defect. A script, the driver's header check and
their tests; nothing under `src` changed.

**The defect.** `scripts/cloud_battery.py` cut each failing id out of
pytest's `-rfE` summary lines with `^(?:FAILED|ERROR) (\S+)`, so an id was
kept only up to its first space. 1,829 of the suite's collected ids hold one,
in 311 groups sharing everything before it, so a parametrized test failing on
the base for the machine's reason would have excused a sibling failing on the
branch for the branch's. It had not fired only because none of the ids failing
on a container held a space. The failing test came first, in `6ad68b07`: a
scratch suite fails `test_case[one two]` as the base and `test_case[one
three]` as the branch, and on the old reader `compare` exited 0, reading the
branch's failure as the machine's; the same for an id holding ` - ` and for an
erroring id.

**The change.** The suite run loads a small reporting plugin, written to a
fresh temporary directory and loaded with `-p`, which at the end of the run
writes the node id of every report pytest's terminal filed under `failed` and
`error`, the very reports the summary lines and the summary's counts are
printed from, on the xdist controller only. `read_report` refuses the run when
the plugin wrote nothing, when its counts disagree with the summary line or it
lists fewer ids than it counts, and when an id cannot be stored whole one a
line (empty, padded, starting with `#`, or holding anything `str.splitlines`
breaks at). The baseline header ends `history full ids whole`; `compare` and
`mutate.py --known-failures` refuse a header without the new field, which is
every baseline written before U268, with the command that measures it again.
The suite command is otherwise unchanged and passes nothing over `addopts`.
Decided by the session: the plugin reads the terminal's own categories rather
than classifying reports itself, so it files a report exactly where the
summary line counts it (strict xpass, a call failure with a teardown error,
an xdist worker crash and pytest's built in subtests included).

**Measured.** A baseline of the base `151746a9` by the old reader and one by
the new reader, run from outside the tree against the base checkout, hold the
identical 161 ids and the same summary (133 failed, 28 errors), so the new
reader recognises every machine bound failure the old one did; none of them
holds a space. `compare` on `34c1b90e` against the whole id baseline: ruff and
the scan clean, 161 still the machine's, 0 newly failing, 0 no longer failing,
18,815 passed. At the merge of `main` the battery ran again; its result is in
the pull request.
