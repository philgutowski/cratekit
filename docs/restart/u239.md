**U239, #647, a label go stopped at the call ceiling finishes its tail on the
next go, built in the cloud lane on 2026-11-10 and 2026-11-11.** Filed from
the attended label pass of 2026-11-10 (Cratekit 0.15.1), whose go over 44
releases stopped at the provider call ceiling after 500 calls with 68 of 106
tracks staged.

**What failed, reproduced on the base.** The ceiling's continue command was
the dispatcher's `crate --calls N job resume JOB`. The job's detached worker
finished the download, and the next `crate --run RUN label sync --go`
refused `decision-stale` over an empty plan: the answers were settled and a
succeeded job is not one a go resumes, so the gate's digest moved and nothing
named the tail. The tests written first failed on the base with exactly that
refusal (exit 11) and that continue command.

**What landed.** In `label/go.py`, a `--go` under a run that holds a recorded
`apply` and whose go queued a download (`own_job`, `_own`) takes that
download on with no new decision (`_carry_on`): a job still open, or failed
with a cause a retry may clear (re-armed first), is driven; a settled one is
read; and its landing is named over the job's own manifest and the pass its
run gives, so `cli/label_sync.py` runs the tail and stops at the landing's
gate. Nothing new is queued, and answers saved since are named as waiting for
the next go. A cancelled job is not taken on, so the gate refuses as before;
an abort recorded after the stop is not taken on either. A go job queued after
it that holds tracks or is still open refuses the tail (`_beside`,
`refused-by-policy`, reused), and `cli/label_sync.py` adds the tail as a
person types it (`_with_commands`, from `_commands`). The ceiling's park of a
go's download now names `crate --run RUN --calls N label sync --go` under the
run whose go queued it, whichever run drove it (`_carried`: the job id moves
to `job`, and the cause names the run with `fresh`); any other park, or a
failure a retry may clear, gains that command as its last step. When the tail
stops at the landing's gate, `cli/label_sync.py` records the landing's run on
the run whose go queued the job, under that job (`landing_role`), so a later
`--go` under that run names the landing and runs nothing; a record of another
run that cannot be kept is the warning `label-sync-landing-unrecorded`.

**Decided here, recorded.** The brief's scenario "a second go with new
answers queued beside a finished job does not land the two as one batch" was
built as two tests: under the stopped go's run, new answers wait and the run
lands its own job alone; and the run's go refuses its tail when a later go's
download shares the folder. A fresh go (a new run) that queues beside an
earlier go's finished but unlanded download still lands both, as it has since
U108, because telling a landed batch from a waiting one needs a landing proof
by pass on both media: a residual with an issue. A cancelled job falls through
to the gate rather than a refusal of its own, keeping the stale refusal that
lets `run decide` answer it again. A `refused-by-policy` was reused rather
than a new reason, so no shared reason table moved.
