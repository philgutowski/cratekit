**U274, #707, a download job logs in once per drive, four provider calls a track in place of six, built in the cloud lane on 2026-11-13.** Filed from the speed survey of 2026-11-12 as an idea; Phillip answered its question on 2026-11-13 with option 1: the session is materialised, validated and written back once per drive of one job, and the private token file is removed when the drive ends or fails. Built on a counting stand in, the in memory keychain and fakes only; nothing reached the live account.

**The engine's per drive seam.** `cli/handlers.run_job`, the one caller of `jobs.drive`, enters a context manager a worker names as its `per_drive` attribute (`PER_DRIVE_ATTRIBUTE`, checked by `per_drive_of` the way U270's batch form is), around the drive and nothing else, so it closes on every way out: finished, parked, interrupted, the no evidence raise, a defect. What the holder notes at its close comes back on the new `DriveResult.warnings`, which `Context.run_job` returns with the drift warnings.

**The vendored drive.** `acquire.cli.handle.per_drive = vendored.drive`. While a drive is open, `VendoredAdapter._session_scope` and `_source` take the drive's hold: nothing is read until the first track asks; the first materialises the token file once (`materialised_session`, unchanged in what it writes) and logs in once; every later track reuses the logged in source, rebound to its own settings, which the reuse branch of `authenticate` still pushes and verifies after asking the gate. Each track still builds its own adapter and takes its own paced acquisition, so the gate, its interval, ceiling, the shared hourly allowance and the pacing delay before each acquisition are untouched. A refusal met at the login, in `offer` or in `fetch` is remembered by the source, and `authenticate`, `offer` and `fetch` raise it again before any call, so a drive never logs in or asks again over a refused session; the worker still parks the job on `AUTH_FAILED`. `AdapterBroken` still fails only its item (R-293).

**The write back.** The tool refreshes an expired access token in memory and writes no file, so before U274 a refresh by the vendored adapter never reached the keychain (measured on the base with the stand in). At the drive's close `provider_session.captured` lays the tool's in memory token fields over the stored session where they differ by value (the tool reads an int expiry back as a float, which is the same value), the result is written into the token file, and `write_back`'s unchanged check writes the keychain once, only when the provider refreshed. A session the tool left in its Dolby Atmos client is not stored. A credential, index or file failure at the close becomes the `provider-session-not-stored` warning and never replaces the drive's own answer; a defect at the close of a drive that returned raises; on a drive that raised the drive's own error is the one reported. The token directory goes in every case.

**A kill mid track.** SIGINT and SIGTERM are recorded by the engine and the drive closes normally. A token directory is now named `cratekit-session-<pid>-...`, and every new scope first runs `provider_session.sweep_orphans`, which removes a directory of that form only when it is a directory, this account owns it, and its process is gone; a live, unknown or unrepresentable process id leaves it alone.
