**Decisions, recorded.**

- **Which count (requirement 2).** The removal's final `localUpdateCount`,
  the value rekordbox gives, read before the commit, not after it. pyrekordbox
  0.4.4's `commit` calls `autoincrement_local_update_count`, which raises the
  count by one per entry of its process wide update buffer; the renumbering
  is SQL and adds no entry. So the final count is `get_local_usn()` plus the
  buffer's length, knowable after the deletes and before the flush, and
  `test_the_stamp_is_the_count_the_binding_s_commit_leaves` drives it: the
  stamp equals the count after the commit, one step per deleted row. Calling
  the binding's own increment before the guard was rejected, since it clears
  the buffer `assert_session_whitelisted` reads and would blind the guard to
  the deletes. A buffer that grows after the stamp is refused before the
  commit, and a count that lands elsewhere is refused at the read back.
- **What forward means (requirement 4, reworded on the issue).** The first
  build refused a stamp not later than the row's old `updated_at`. The
  battery's behaviour scenario showed two clocks: its library comes from a
  template an earlier test built under the real clock, while the scenario's
  clock is held in the past, so every removal refused. A real library has the
  same shape, rows another machine stamped. Forward is now judged on the
  removal's own clock, the stamp no earlier than the plan's reading, and a
  row's old time is refused only when left as it was. Review round one drove
  a row holding `2099-01-01` through the verb: it commits and moves back to
  now, which is what rekordbox does.
- **The no stamp rule stays.** `tests/test_rb_writer_guard.py`, never edited,
  calls the confinement with no stamp and expects `TrackNo` alone admitted,
  so that rule is kept for a caller planning no stamp, and a stamp column
  moving under it is refused. The one production caller always passes a
  stamp, which mutation row S26 kills.
