**R-1091 built, 2026-11-01, in the cloud lane on
`cloud/410-a-full-label-playlists-build-sto`, issue #410: a full `crate label
playlists LABEL` keeps every release it reads, so a large label builds over
several runs instead of starting over each time.** A new module,
`src/cratekit/label/kept_reads.py`, keeps one JSON document per label under
the installation state entry `label_crawl_cache` (`label_crawl/<label>/reads.json`),
beside the verifier's own cache, since that entry already declares a
catalogue answer replayable and library agnostic; the brief's "library
state" was read as the product's state, and a library scoped copy would read
the same releases again for every library. Each read keeps the release's
track identifiers with whether each plays, the year the provider stated, and
when it was read, and a release the provider no longer has is kept as gone; a
failed read is never kept. A read stays true for `KEPT_FOR`, seven days, the
recommendation put to Phillip on the decisions page (the document
`410-read-age-1`), and one from the future is read again. The store is written
every 50 new reads and again whenever the read ends, a breaker park or a
refusal included. A document that cannot be read, is another version, names
another label or holds an entry of the wrong shape refuses
`label-playlists-reads-unusable` before the listing or any release is asked,
and is never rewritten. A write the filesystem refuses (a full disk, a read
only volume, a file where the label's directory belongs) is said on the build
gate's screen and as the warning `label-playlists-reads-unkept`, and is tried
again at the next write: the store costs the next run its reads, never this
run its plan. The full build loads the store first, reads through it in
`_grouped`, and both screens count the reused reads and name the oldest. The
crawl gate asks over the calls still to make, the releases not kept fresh,
and keeps its digest over the listing's count, so a run resumed under the
same answer is not stale; the build gate's digest is the plan's identity
alone, as before. The listing is NOT kept, against the brief's approach: a
kept listing would hide a release the label put out since, and U191's test
that a grown listing asks the crawl gate again pins that, so the listing is
read again by every run and its cost is a residual. `--releases` and
`crate organize`, through `plan_label`, are handed no store and behave as
before. GUIDE says how a full build keeps and reuses its reads.
