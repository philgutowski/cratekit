**The write back.** `provider_session.materialised_session` hands
`write_back` the session it read, and `write_back` writes nothing when what
the tool left is the same value, compared as the bytes `secrets.set_json`
would store (key order and spacing in the file are not a change, a value that
changed type is). A changed session is written exactly as before, through
`secrets.set_json`, the index lock, the read back and the index. This holds
for every user of the scope: the catalogue, the account, the vendored
downloader and streamrip.

**One login per process.** `provider_session.session_for(cfg)` holds a
`HeldSession` (gate, logged in client, app client, the bytes the keychain
holds for it, the gate settings it was opened under). The first use logs in
exactly as `client_session` did (gate, materialise, `load_oauth_session`, the
typed failures; nothing is held unless all of it succeeded). A later use under
the same settings asks `gate.assert_open()`, reads the keychain once and makes
no request, reusing the client only while the keychain still holds the
session it was opened from; a session replaced since is logged in afresh, and
a keychain that answers missing, rejected or unavailable raises the same
translation a login raises and drops the hold. `tidal_catalogue.open_catalogue`
and `tidal_account.open_account` take it, so each still builds its own adapter
over the shared client. The app client is held with it, which answers R-1218
(one token request for a process that opens both).

**Refusals.** A 401 or 403 answered or raised through the shared client's
transport drops the hold (`_watch`), whichever seam made the call.
`account.provider_failure` drops the adapter and the session it was built
over (`_forget_refused`, round one's R4); `account.forget` drops every hold,
which the conftest guard calls on both sides of every test. The account's
held adapter is handed out only while the session it was built over is still
the held one.
