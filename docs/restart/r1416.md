**R-1416, #620, a pair whose account order is not kept keeps rekordbox's
order on its first sync rather than taking the account's for good, built in
the cloud lane on 2026-11-07.** A large card: it changes what `crate sync
pair` writes into rekordbox on a pair's first sync. Filed from Phillip's
answer on #608 (decision 608-outside-order-2), which departed from the
recommended option: outside GIG READY Tidal's order is never written (U231),
so a hand pair of Tidal 1, 2, 3 and rekordbox 3, 1, 2 had rekordbox put in
1, 2, 3 at its first sync, and the DJ's arrangement was lost for good.

**What landed.**

- **A first sync whose account order is not kept is led by rekordbox**
  (`sync/pair_merge.merge`, new keyword `order_kept`, default True). With no
  base, no stopped write handed in (none was found, or the account stands
  off its path) and rekordbox holding a track, rekordbox leads: its tracks
  keep their order, and each track only the account holds is placed after its
  neighbour there by `placed`, as a follower's additions already are. Tracks
  only rekordbox holds are appended to the account as before.
- **Told, not asked.** `plan_pair` reads `_keeps_order` once before the
  merge and passes it in, and the U231 account write reuses the same value,
  so the merge and the write cannot disagree on the scope.
- **Unchanged:** a kept order (under GIG READY, or with
  `outbound.pair_order_every_pair` on) lets the account lead as before; a
  stopped write handed in keeps U225 and R-1376's rule; an empty or new
  rekordbox playlist is led by the account as before; every base rule,
  R-1404's included, is untouched. The next sync reads a base whose sides
  disagree, so R-1404's rule keeps rekordbox leading until the account
  changes order, which brings Tidal's whole order (608-outside-order-1).
- The gate line says "order follows rekordbox's; the account's order is kept
  only for pairs under GIG READY, so it is left as it is there", U231's
  existing wording, and never that it follows the account's.
