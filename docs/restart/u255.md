**U255, #684, exporting a set to the account costs two requests a track, not
four, built in the cloud lane on 2026-11-12.** Filed from the speed survey of
`main` at `a7fcc9f4`: adding a track to an account playlist made four provider
requests, three of them the same GET of the playlist, because the client's
`Session.playlist` fetches an owned playlist twice (a `Playlist`, then the
`UserPlaylist` its factory builds), `TidalAccount.add_to_playlist` opened the
playlist afresh for every track, and the client's own add reads it again after
its POST for the next version tag. Every request waits at the provider gate and
counts against the command's ceiling.

**What landed.** `TidalAccount` holds, per playlist, the client object its
membership read opened (`_opened`, beside `_members`), and `add_to_playlist`
adds through it. The membership reads the tracks through `copy.copy` of the
opened object and holds the opened object only once that read has succeeded,
so the held object's version tag and its length, the add's `toIndex`, always
come from one answer: its open, or the client's own read after the previous
add. A failed add drops the hold, and the one retry the write policy allows
(`WRITE_RETRIES`) opens afresh through `_playlist`, on the open's own retry,
and sends the add once more; a 412 on a stale tag now lands on that retry,
where before the retry resent the refused tag on the same object. An answer
that does not name the track is read back on a fresh open as before. Every
open goes through `_playlist`, which drops the hold first, so an object another
member wrote through is never reused. On the real client over a counting
transport, 10, 100 and 1,000 adds make 23, 203 and 2,003 requests (12, 102 and
1,002 GETs of the playlist, one tracks read, one POST a track), against 43,
403 and 4,003 on `main`. The gate, its interval, its ceiling and its state
file, the ledger reserve and the ledger record per track are untouched, and
each add sends the same form it sent, one track, at the playlist's length,
duplicates and missing tracks skipped.

**Tests**, `tests/test_outbound_add_requests.py`, 22, on a stateful transport
under the real client that keeps each playlist's items, moves its tag on every
write, answers a stale tag 412, and can serve a write between the open and the
tracks read, a read one write behind, a failed tracks read and failed opens.
The request count is the assertion. Ten fail on `main` (the counts, the retry
on a fresh open, and a write between the open and the tracks read), and five
failed on round one's head.

**Decided here, recorded.** The brief's further saving, opening a playlist
with one request as the listing does since R-1016, is not taken: it would
change the open every member uses, so it is its own card if wanted, and the
bound the brief asks, K + 2 GETs, is met without it. The object
`create_playlist` returns is not held, so a new playlist's first add still
opens once. The hold drops first written into the two removals and the folder
move were taken out in the fix round: a deleted playlist's add is refused by
its POST either way, and a folder move does not change a playlist's length.
