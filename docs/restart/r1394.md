**R-1394, #604, an order stopped part way is finished only from a reading
its moves could have left, never from a lag that two readings agree on,
built in the cloud lane on 2026-11-07.** A large card: it changes what the
account order write of `crate sync pair` records as it sends its moves and
what the next plan sends from a stopped write. Filed by U231's round one
review (#595): a write stopped part way through its order was finished from
the leading side once two readings five minutes apart agreed on an order on
the moves' path, so a provider serving the order from before the moves for
longer than that had the remaining moves sent by position from the lag,
leaving d, c, b, a for an asked d, c, a, b.

**What landed.**

- **The record says how far the moves can have got**
  (`sync/pair_stopped.py`, `sync/pair_cli.py`). The `moving` step gains
  `sent`, the moves that may have reached the provider, and `landed`, the
  moves it accepted. `begun` records both at 0 and answers a recorder the
  adapter calls before each send, so while move i is in flight the step reads
  `sent = i, landed = i - 1`, marked and carried (R-1372) before the move is
  sent: a record that cannot be written sends no further move, and both
  counts are bounds by construction. A `moved` step reads as every move
  landed; counts missing (a write before this card) or not fitting the
  write's moves read as nothing known, none landed and every one maybe sent.
- **The adapter tells it** (`modules/outbound/tidal_account.py`, the protocol
  in `modules/outbound/service.py`). `order_tracks` calls the recorder
  `begun` answers before every send, a resend included, and after each 412,
  which changed nothing (Sitting 62), brings `sent` back down before the
  pause, so a stop inside the pause reads true (round one's fix). Any other
  failure of a move leaves its landing not known. A `begun` that answers
  nothing keeps U231's contract, so every fake of `order_tracks` kept its
  signature while #597 was built beside this.
- **The plan finishes only at or past what was sent** (`_pending`,
  `pair_stopped.positions`). Once two readings agree, an order on the moves'
  path is finished from only when some count of moves at or past `sent`
  leaves it. Before `landed` it is a lag, held however long it agrees, as an
  order whose every move was accepted already was; at `landed` with a move
  whose landing is not known after it, it is held too; off the path it is
  the person's change, merged as theirs, as before. A write whose first move
  ended on its 412s records `sent = 0`, so a reading at the start finishes it
  once from there. `_settling` names which hold it is, with the counts in the
  detail.
- **The finishing write is held to the agreed reading** (round one's fix,
  `_write_account`). A write that finishes a stopped order and adds and
  removes nothing on the account passes the check's listing as `expect`, so
  the adapter reads again a reading that lags the stopped moves seconds after
  the plan's and refuses with nothing moved, rather than move by position
  from it. With additions or removals the membership check stands (residual
  `r1394-c`).
- **A refused finish hides nothing** (round two's fix, `stopped_writes`). A
  pending record now outranks a later one that sent no move, as a later run
  stopped before its order began already hid nothing (U225), so the refused
  finish's ordering step no longer stands in for the pending write and the
  next plan holds a lag rather than merge it into rekordbox.
- `docs/GUIDE.md` says what a DJ sees of a stopped order.
