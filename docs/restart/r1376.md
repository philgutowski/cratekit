**R-1376, #597, a pair whose rekordbox side was released after a stopped
order and paired again finishes that order on its first sync rather than
writing the stopped write's scramble into rekordbox, built in the cloud lane
on 2026-11-07.** A large card: it changes what the first sync of `crate sync
pair` plans to write into rekordbox. Filed by R-1372's round one review: the
U225 stop, the pair's rekordbox playlist deleted, a sync that released the

nothing said of the stop.

**What landed.**

- **A first sync reads the stop on its account playlist.**
  `_Reader.first_stop(account_id)` in `sync/pair_cli.py` answers the latest
  write that stopped part way through ordering the account playlist and that
  no later run finished, as `_Reader.stopped` keeps it from the kept steps and
  R-1372's carried records, whatever the pair's mark. `plan_pair` asks for it
  on a first sync, one with no pair record (a hand pairing before its mark) or
  one with no snapshot (marked, never written whole), when the pair's own rule
  found no stop.
- **For its order alone.** The path check U225 built (`pair_stopped.reached`)
  decides whether the account stands where the stopped write's moves could
  have left it; when it does, the account is read as the write would have
  left it had it finished, and the merge reads each side's change of order
  against what that write left, so the side that led it leads again unless a
  side changed order since. Nothing of the stop is folded into a base, since
  a first sync has none and the stop's bases are another pair's, and the gate
  names a fold only where one was made (`folded` needs a snapshot).
- **The gate names it** with U225's existing line, "finishes run RUN's write,
  stopped part way through its order, so its moves are not read as
  anybody's", and its `sync-pair-finishing` note.
- **Held when pending.** U231 (#595) landed while this card was built and
  holds a pair whose stopped write sent its moves with no read back
  (`stopped_write.pending`) until two readings agree. A first sync's stop is
  read before that hold, so a pending order it reads is held as any pair's
  is rather than finished from a reading U231 says cannot be trusted, and
  `_pending` reads no kept reading when the pair has no record.
- The pair's own rule, `_Reader.stopped_write` with R-1372's mark guard, is
  unchanged, as the card asked that every existing refusal stay.
- `docs/GUIDE.md` says a first sync after pairing the playlist again finishes
  the stopped order.
