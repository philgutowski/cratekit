**U961, #1080, `crate run show` shows a waiting gate's whole screen from the
run record, so any process can show it without running the verb again, built
in the cloud lane on 2026-11-25.** An engine card of the menu bar app, idea
#377, whose decision 4 has the app show a gate's plan and digest and answer
it with a tap; #1081 (U962, the app's answer bound to the digest it showed)
and #1087 (U968, the gate view) read what this card keeps.

**Who built it.** Planned and built by a thread on Opus 5.5 at xhigh, a large
card since it adds a write to the run record. **Review: Opus 5.5 at high
effort, Fable out of usage**, a general purpose agent given the
`fable-reviewer` brief, two rounds, each in its own worktree and venv.

**What landed.**

- `gates.Gates.require` keeps the screen each refusal shows, on the run under
  the gate's name, through one helper, `_keep`, at its four refusals: an open
  gate, an explicit gate's refused inline answer, an option the gate does not
  offer, and the gate's own stale over a moved plan. It is set on the same
  `RunState` as the offer `require` records, so the dispatcher's one save
  writes both, and a later refusal at the gate replaces screen and offer
  together. A gate that passes drops its screen, and so does `gates.record`,
  since run records are never pruned: `run decide` and `run retire` leave a
  record as small as it was.
- `gates.Screen`: the kind (`open`, `stale`, `unknown-option`, words of their
  own, never a cause's reason), prompt, options, explicit, the offered digest
  (None for a gate with no digest source), `shown` as given, the pins the run
  holds for the gate, when it was kept, and the cut. `shown` goes through JSON
  as the refusal's envelope does, and is written as JSON text, so the order
  its facts were shown in survives the record's sorted keys and `run show`
  prints the screen line for line as the refusal did. `RunState.screens` is
  written only when set, so `RUN_SCHEMA_VERSION` stays 1 and a record from
  before this card loads unchanged; an entry that is not a screen is left out.
- **The size bound.** `gates.cut_shown` holds a kept `shown` to
  `SCREEN_LIMIT`, 64 KiB of compact JSON. Past it every list keeps its first
  items, the same number for each and as many as fit, every other fact stays,
  the digest and the count among them, and the cut names each list shortened
  with how many it kept and left out; when the facts alone pass the limit only
  the digest and the count stay and the cut names every fact dropped. **The
  limit's reason:** every reader that scans the run records reads each one
  whole (the sibling warning on each gated database verb, `run decide`, `run
  retire`, the doctor, `crate status`), so a plan of thousands of items kept
  whole would slow every gated verb; 64 KiB keeps a few hundred plan items,
  more than a person reads on one screen, and the verb run again with `--run`
  shows the rest. The refusal itself is never cut.
- `gates.waiting`, the one reader: a gate waits when it is the open gate,
  when the run offered it a plan and holds no answer, or when its answer binds
  another plan than the offer or an option the screen does not offer. A kept
  screen is shown only while its digest is the run's offer for its gate and
  its pins the run's; the latest current screen of a waiting gate is named,
  else the open gate or the first waiting gate by name with the reason no
  screen can be shown.
- `crate run show` carries it as **`data.summary.gate`**, not the brief's
  `data.gate`: the `diagnostic/1` payload declares `checks` and `summary`
  alone and `output.payload_problems` refuses any other field. The brief was
  corrected in its body and the orchestrator corrected #1087's. Its keys:
  `name, kind, prompt, options, explicit, digest, shown, pins, cut,
  writes_database, answer, continue, screen_missing`, null when nothing
  waits. A gate with no screen to show carries `screen_missing`, its reason
  and `gates.continue_command(state)`, with no digest, plan or pins.
- The human `run show` prints the kept screen through `render.render_gate`
  from the fields the refusal carried (the stale screen's first line
  included), a cut said above the screen with the command that shows it
  whole, and a missing screen's reason and command.
- `tests/test_run_show_gate.py`, 36 tests: the brief's seven scenarios
  (refused in one process and shown by `run show` in another, both real
  interpreters; a stale refusal replacing screen and offer together; an
  answer recorded and the run continued leaving the gate null; a record from
  before this card naming `screen_missing`; an oversized plan cut with its
  count and digest kept; an unknown option's screen kept and shown with its
  prompt and run; the human rendering equal to the refusal's, line for line),
  and the reader's edges.
- Unchanged, by the build's constraint: what a gate offers, when it refuses,
  every refusal's detail and printed screen, who may answer, `run decide`'s
  and `run retire`'s output, and the sibling warning. Round two drove a full
  session through both builds, with and without the drop in `record`, and
  found every envelope, refusal, screen, warning and exit code the same.
