**U216, #530, `crate sync pair` never brings into rekordbox a playlist an
adopted account folder already held, built in the cloud lane on 2026-11-05.**
Filed from sitting 59, where a rehearsal on v0.7.0 planned 18 rekordbox
`create` items, `DOWNLOADED Afro_House`, `DOWNLOADED Techno` and sixteen more,
out of the account's `Genre Trivia!` root folder, which U198 had adopted
(`created: false`) with those playlists already inside. The failing test came
first (`33eda14`): on the fake account the second sync planned `DOWNLOADED
Techno` and `DOWNLOADED House` as rekordbox creates.

**What landed.** Decided by Phillip on 2026-11-04, a sync brings to rekordbox
only a playlist made on the account after its root folder was synced.
`sync/pair_cli._discovered_back`, where an account playlist becomes a
rekordbox `create`, now leaves out and names two more kinds, each a `Listed`
row on the gate and in the `sync-pair-not-brought` warning:

* **`before`**, one the folder held before a sync adopted it
  (`pair_discover.before_adoption`). The adoption now records what the folder
  held: `MadeFolder.held` in the pairs document, the ids the plan listed in the
  folder it adopts, carried on `Place.held` and written by
  `PairStore.reserve_folder` in the same locked write that records the folder.
  A folder the product created records an empty set. A folder adopted before
  U216 has no such record, and is read by time: the new account read
  `folder_playlists_dated` gives each playlist's creation time off the same
  folder pages (the client's playlist parser reads `created`), against the
  adoption moment, the earliest `marked` of a pair made in that folder
  (`pair_discover.adoption_moment`). Every unknown (no record, no time, a time
  without a zone, no made pair to date the adoption) reads as held, so it is
  named and never made.
* **`copy`**, a `DOWNLOADED ` copy of a playlist a pair in the same folder
  holds, or of one this same sync brings in beside it
  (`pair_discover.downloaded_copy`): less the mark's prefix, both titles read
  less the folder's own prefix, ignoring case, in adopted and created folders
  alike.

A playlist made after the sync, in an adopted or a created folder, still
comes in as U202 built it. Each reason ends with the step to sync it anyway:
make or choose its rekordbox playlist and pair the two with `crate sync pair
ACCOUNT_ID --rekordbox PLAYLIST_ID`. `docs/GUIDE.md` says so. No beat grid is
touched, and no new write path: the creates stay behind the same rekordbox
gate.

**Decided conservatively, recorded here.** An unknown is read as held, since
one read as new makes a duplicate and one read as held is only named. The
pairs document stays version 2: a record without `held` reads as a folder
adopted before U216, so a copy that drops the field costs a playlist named,
never one made twice. A plan held by a build before U216 decodes `Place.held`
as None, and the adoption is then recorded as unknown rather than empty. The
`DOWNLOADED` comparison ignores case and nothing else. Card size large.
