**U272, #701, a capture's copy is on the disk before its manifest says it is
verified, built in the cloud lane on 2026-11-13.** Filed from the speed survey
of 2026-11-12 as a question; Phillip answered on 2026-11-13, option 1: flush
every capture, the copy, its sidecars and its directory, before the manifest is
written. The full flush on macOS was left to the build, and the conservative
reading, ask for it, is what landed. Large by METHOD: it changes the path every
guarded write takes its restore point on.

**The seam, `snapshot.capture`**, the one function all twenty guarded write
callers and every rehearsal of one take their capture through. After the copy,
the hardening and the integrity check, `_flush` walks the finished capture
deepest first and flushes every file, every directory, the capture directory
and then the store that holds it; only then is the manifest written. After the
manifest the capture directory and the store are flushed again, so the record
itself survives before anything commits behind it, since the shared atomic
writer syncs the manifest's bytes but not the directory its rename changes.
Derived by walking, as `_harden` is (P3), so it covers what the writer's
`snapshot_db` copied (the database, its companion files, the legacy playlist
file) and the coupled half without a list. `os.walk` is told to raise on a
directory it cannot read, since by default it skips one. The flush runs after
the check, not before: the check opens the copy, and the review drove the real
check's close removing an open log's files from the capture.

**A failed flush is never recorded as verified.** Before the manifest or after
it, a flush that fails rewrites the manifest with `integrity_verified` false
and refuses with `snapshot-integrity-failed`, naming the file and the
operating system's error, remedy `mount-library-volume`. Refusing rather than
returning an unverified record means no caller can commit behind it even by
forgetting to ask; the twenty callers ask anyway. If even that manifest write
fails the refusal still stands. One double failure after the manifest, the
late flush and then the rewrite, leaves the manifest saying verified about a
copy that was flushed, with the capture refused all the same; the `Capture`
docstring says so.

**`config.flush_to_disk`**, the third durability primitive beside the atomic
writer and the durable append, for bytes another writer put on disk. It opens
the path read only and asks for `F_FULLFSYNC` where the platform has one,
read from `fcntl` and never spelled, so macOS empties the drive's own cache;
it falls back to `fsync` only when the filesystem answers that it has no full
flush (`ENOTSUP`, `EOPNOTSUPP`, `EINVAL`, `ENOTTY`), as SQLite does, because
refusing there would leave every write on such a drive with no restore point
at all; every other error from either flush or the open raises, renamed to
carry the path since a descriptor's error names none. Windows skips a
directory's flush, which it cannot open. `core/jobs.py`'s directory flush,
which ignores its errors, was deliberately not reused.

**Unchanged:** what is copied (`_copy`, `_copy_file_set`), what is checked,
the existing refusals. The disposable copies and the rehearsal's scratch copy
of the database, which carry no manifest, are not flushed. Out of scope by the
plan: the restore's copy back to the live library, the atomic writer's own
directory flush, the backup feature (an external copier, not a capture).
