**What landed.**

- `core/held_plan.Steps`, a steps file per run beside its held plan, bound to
  the plan's digest, written atomically on every step and released with the
  plan. `load_steps` answers no steps, and says why, for a file that cannot
  be read, of another version, run or plan.
- `sync/pair_cli.apply_pair` records each pair's steps as they land:
  `making` before a made account side is reserved, `made` once it is made and
  in its folder, `rekordbox` with the memberships the guarded commit left,
  `queued` with the job id, `account` before the first account call,
  `ordering` before the first move of an order, and `done` once the snapshot
  is recorded. A step that cannot be recorded stops the write with
  `sync-pair-steps-unwritten`. The record file is written before the first
  write, so an unwritable one refuses before anything is written.
- A continue of the run passes over pairs done and starts each other pair at
  its first unfinished step under the answers already given:
  - a made side recorded is not made again;
  - a reservation the stop left is moved into its folder (only a pair the
    pairs document records as made for this rekordbox playlist in this
    folder) and filled;
  - a landed commit is read back, not written;
  - a queued job is not queued again;
  - the account writes are begun again whole, since each skips what the
    playlist already holds as asked.
- `check` (U209's, its body kept whole) is made step aware:
  - it reads no pair done;
  - it reads a part written account playlist for what its own write could
    have done and nothing else (`_beyond`): no track gained but its
    additions, none lost but its removals, and the order the plan read kept,
    additions after it, until the write began to order;
  - it reads a landed commit's playlist against what the commit left;
  - it does not read as moved the playlist, the folder, the job or the
    pair the run made;
  - steps that could not be read are named on the stale refusal.
- `_asked_before` lets the held plan be read back after the run's own marks.
  A sync of every pair asks for every marked pair, and the pairs the write
  made or first marked are read as the plan read them.
- `sync/pair_calls.py` estimates a write's provider calls from the account
  adapter's shape, held exactly to the shipped adapter over a counting fake
  client (`tests/test_sync_pair_calls.py`). The gates show what the command
  that writes is expected to spend (check and write) against the ceiling it
  runs under. When the ceiling is lower they say so and name a `--calls`,
  the estimate with a quarter's margin rounded up to a hundred, with the
  command to give it to.
- A park part way through the check or the write says how many pairs
  finished and names the run.
  - A ceiling stop names a `--calls` sized from what is left, never below the
    ceiling it stopped at, and the dispatcher's `continue_command` carries
    `--run` for a cause that names a run.
  - Any other park names `crate --run RUN` and the verb's words, to give once
    it has passed.
  - A run whose plan could not be held recorded no step, says it cannot be
    continued, and its continue command starts a new run (`fresh`).
- The answer carries `totals.finished_before` and `totals.calls_expected`
  beside U209's `totals.calls`, and the `sync-pair-resumed` warning on a
  continue.
